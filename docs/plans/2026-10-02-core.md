# ClauFlip implementation plan

**Goal:** Retain multiple official Claude Code subscription logins and manually switch the active login while preserving shared local configuration and conversations.

**Architecture:** A small Go CLI patches only account-owned authentication fields in the existing Claude configuration. No proxy, environment mutation, per-account configuration tree, background refresh, telemetry, hooks installation, or automatic account rotation. Official Claude owns authentication and refresh. Stop Claude before switching; reopen with `claude --continue` or `claude --resume` afterwards, as confirmed by the user.

**Tech stack:** Go, native credential storage adapters, standard testing package, GitHub Actions on Windows/macOS/Linux.

## Design

- Commands: `login NAME`, `save NAME`, `list`, `use NAME`, `remove NAME`; `recover` only for interrupted writes. Official login runs in a temporary private configuration with child-local environment overrides, then imports only account fields. Main configuration is never used for onboarding. No logout calls.
- Account fields: complete `claudeAiOauth`, optional `trustedDeviceToken`, complete `oauthAccount`. Other JSON values and files are never replaced with per-account snapshots.
- State: private local vault, bound to the exact Claude configuration; no credentials in repository, logs, arguments, or network requests. Save outgoing live credentials before switching. Refuse unknown/malformed state, mismatched identities, and missing live OAuth rather than overwrite a saved login.
- Consistency: exclusive OS lock; active-Claude guard; atomic writes; durable pre-write journal. Recovery restores only account fields and retains unrelated edits. Failed official login restores the previous account. Expired/revoked refresh tokens may still require official reauthentication.
- Cross-platform: native macOS Keychain/file fallback; Windows/Linux official credential file. Respect existing configuration directory and macOS secure-storage override without setting environment variables.
- Auth environment overrides remain unchanged and trigger a visible warning that `/status` must confirm the effective account.
- Scope limitation: local hooks/config/history are preserved; account-hosted policies and connectors belong to the selected account.

## Task 1: Evidence and contracts

Read official authentication/CLI docs and current high-star repositories. Record stars, maintenance and specific unresolved issues; do not claim an upstream is bug-free or ban-proof. Define platform IO and core state interfaces before independent implementation.

## Task 2: Transactional core

Create `internal/accounts` with tests first. Run failing tests for narrow field replacement, refreshed outgoing token capture, unchanged settings/history, corrupt stores, missing OAuth, duplicate account identities, failed second write, interrupted transactions and concurrent writers. Implement only the operations these contracts require; rerun `go test ./internal/accounts`.

## Task 3: Platform adapter

Create `internal/platform` with tests for path resolution, process detection and lock/atomic write behavior. Implement official credential backend, private state directory, OS lock and official login runner. Do not access real user secrets during tests. Run package tests and cross-build Darwin/Linux/Windows.

## Task 4: CLI and documentation

Create `cmd/clauflip`, concise Chinese README, MIT license, reference audit, compatibility record and CI. Test usage, redacted listing, invalid names/commands and end-to-end switching against temporary fixtures.

## Task 5: Review and delivery

Independent gpt-6.1-sol review for requirement coverage and credential-loss paths. Fix material findings. Run all tests, vet, cross-builds and GitHub Actions. Create a separate GitHub repository, commit and push only reviewed source/docs. The user selected the name ClauFlip and explicitly requested public MIT open source; check source and history for private data before making it public. Deliver binary paths and exact validation limits; real account logins require the user's browser interaction.
